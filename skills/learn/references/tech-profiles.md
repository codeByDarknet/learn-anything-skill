# Technology profiles

Pick one or more profiles. For each: what to install, the playground, how exercises are graded, typical module arc, capstone ideas. These are starting points — adapt to the exact technology, the learner's goal and level, and **current** tool versions (check them).

---

## A. Programming language

**Install:** official toolchain (version manager if idiomatic: rustup, pyenv/uv, nvm/fnm, sdkman, asdf/mise), formatter, linter, language server, editor extension, debugger.
**Playground:** `playground/` with a scratch project + instructions for the REPL if one exists (python, node, iex, dart via `dart run`, `go run`, `cargo run --example`), and a link to the official online playground.
**Grading:** native unit tests (see `exercises.md`). Benchmarks for performance exercises. Race detector / sanitizers where available (`go test -race`, `cargo miri` optional).
**Arc:** intro & toolchain → values, types, control flow → functions → collections → the type system (structs/classes/traits/interfaces) → error handling → memory model (ownership/pointers/GC) → modules & packages → testing → concurrency/async → I/O, files, JSON → networking/HTTP → persistence → idioms & design → capstone finish (package, release, CI).
**Capstone ideas:** CLI tool (task manager, file organizer, log analyzer), REST API with DB and auth, TCP chat server, interpreter for a tiny language, static site generator, rate-limited web crawler.

## B. App framework (web, mobile, desktop, backend)

**Install:** language toolchain + framework CLI (Flutter SDK + `flutter doctor`, Node + create tool, JDK + Spring Initializr, PHP + Composer + Laravel installer, Python + uv...), emulator/simulator or browser devtools, DB if needed (via Docker).
**Playground:** a sandbox app generated by the official CLI; for mobile, emulator setup + "run on your phone" instructions; hot reload explained.
**Grading:** framework test tooling — widget/integration tests (Flutter `flutter test`, `integration_test`), component tests (Testing Library + vitest), request tests (Laravel feature tests, Spring MockMvc, pytest + TestClient), E2E (Playwright) for milestones. Snapshot/golden tests for UI when stable. Lint and type-check as extra gates.
**Key rule:** the learner **builds one real app through the whole course** (the capstone). Small exercises isolate a concept (a widget, a hook, a middleware), then the milestone applies it to the app.
**Arc (Flutter example):** Dart essentials → widgets & composition → layout → state (setState → provider/riverpod/bloc as chosen) → navigation → forms & validation → networking & JSON → local persistence → async & streams → theming & responsive → testing → platform features (camera, notifications) → performance → release builds & store prep.
**Capstone ideas:** app for a real need (shop catalog + orders, habit tracker, expense splitter, recipe planner, event check-in with QR), with backend or local-first.

## C. Infrastructure / DevOps

**Install:** Docker (or Podman), the tool CLI (kubectl, helm, terraform/opentofu, ansible), local cluster (kind or k3d recommended; minikube as alternative), `jq`/`yq`, linters (hadolint, kubeconform, tflint).
**Playground:** fully local and disposable: `playground/kind.yaml` (multi-node if relevant), `docker-compose.yml` with sample apps, a tiny demo app (with Dockerfile) to deploy, `make up` / `make down` or scripts. Terraform: providers that run locally (docker, local, kind, random) or LocalStack; never real cloud by default.
**Grading:** `check.sh` asserting live state (kubectl jsonpath, `docker inspect`, `curl`, `terraform state list`, `ansible -m ping`), plus static validation. Break & repair scenarios via `setup.sh`.
**Arc (Kubernetes example):** why orchestration → cluster anatomy & kubectl → pods → deployments & rollouts → services & networking → config & secrets → storage → ingress → health probes & resources → scheduling → RBAC & security → Helm/Kustomize → observability → GitOps/CI deploy → troubleshooting marathon.
**Arc (Docker example):** containers vs VMs → images & layers → Dockerfile best practices → volumes → networks → compose → multi-stage & small images → security (non-root, scanning) → registry & CI build → debugging.
**Capstone ideas:** containerize and deploy a 3-tier app (frontend, API, DB) with CI, zero-downtime rollouts, monitoring and a runbook; "platform for my side projects".

## D. Cloud platform

**Install:** provider CLI, credentials setup **only when the learner opts in**, IaC tool, emulators (LocalStack, Firebase Emulator Suite, Azurite, Supabase local).
**Safety:** default to emulators and free tier; every lesson touching real resources has a **cost box** (what it costs, how to stay free) and a **cleanup** command; recommend a budget alert in module 00; never create resources without explicit confirmation.
**Grading:** checks against emulators (`awslocal s3 ls`), IaC plan/validate, CLI queries on real resources tagged `learn-<course>` when opted in.
**Capstone ideas:** serverless API with auth and storage, static site + CDN + CI, event-driven image pipeline.

## E. Data store / query language

**Install:** the server via Docker Compose (pinned version), CLI client (`psql`, `mongosh`, `redis-cli`), a GUI option.
**Playground:** compose file + seed dataset realistic enough to be interesting (e-commerce, library, flights) + reset script.
**Grading:** run the learner's query/file, compare output to expected (normalized), check schema via catalog queries, check `EXPLAIN` uses an index for performance exercises, check constraints by attempting invalid inserts.
**Arc (PostgreSQL):** relational model → SELECT basics → filtering & sorting → joins → aggregation → subqueries & CTEs → window functions → DDL & constraints → transactions & isolation → indexes & EXPLAIN → functions/triggers → JSONB → backup/replication basics → using it from an app.
**Capstone ideas:** design and optimize the database of a real product; analytics dashboard queries.

## F. Developer tool / workflow

**Git/GitHub:** exercises operate on **real repositories**: `setup.sh` creates a local repo in a specific state (conflicting branches, a lost commit, messy history); checks inspect `git log --format`, `git status --porcelain`, refs. GitHub parts (PRs, Actions, branch protection, releases) use `gh` on a learner-owned **private** repo created only with explicit consent; checks query `gh api`. Capstone: maintain a small open-source-style project end to end.
**Shell/Bash, regex, Vim, Make:** checks run the learner's script/pattern on fixtures and compare output; Vim via `vim -es` scripted checks or keystroke challenges in `answers.md`.

## G. Data / ML / scientific

**Install:** Python via uv or conda, Jupyter, the libraries pinned in `pyproject.toml`; GPU optional and detected.
**Playground:** notebooks + datasets (small, bundled or downloaded by a script with checksum).
**Grading:** pytest on functions extracted from notebooks (or `nbval`/`testbook`), numeric tolerance assertions, model metric thresholds on a fixed seed.
**Capstone ideas:** end-to-end analysis or model on a dataset tied to the learner's interest, with a report.

## H. Concept-heavy domain

Networking, security, algorithms, system design, OS internals: labs with real tools (Wireshark/tcpdump captures, `dig`, `openssl`, containers as hosts), small implementations with tests (implement a hash map, a rate limiter, a DNS resolver), predict/quiz exercises, design documents reviewed with a rubric in tutor mode. Security labs only against local, intentionally vulnerable targets the course sets up (e.g. in Docker) — never against third-party systems.

---

## Choosing versions and tools

- Prefer current stable/LTS. Record exact versions in `course.json.tools` and SETUP.md.
- Respect what is already installed if recent enough; don't force upgrades without reason.
- Prefer the ecosystem's default choices (official CLI, default test runner) over niche ones; mention alternatives in one line.
